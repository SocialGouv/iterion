This addendum **refines the approved shared-queue activation barrier**. It preserves the same NATS broker/account, `ITERION_RUNS` stream, `iterion-runners` consumer, lease system, Engine and RunStore. It does not replace the approved plan or reduce its remaining contract, runtime, composition, authoring or compatibility work.

The separate-native-stream candidate is rejected for this implementation. It changes the approved queue topology, may constitute the prohibited second queue, and still requires credential exclusion and protection against old `EnsureSchema` callers. It therefore does not remove the missing authorization proof.

### 1. Establish the supported authority contract

Implement one bounded distributed profile: **a finite, static NATS authorization configuration, supplied by the trusted deployment operator, reconciled through NATS system access and the Kubernetes API**. Allow named accounts with password or nkey users, publish/subscribe allow and deny rules, and `default_permissions`. Define an explicit schema of supported operational and authorization keys and reject unknown keys. Reject imports/exports affecting protected resources, leafnodes, gateways, websocket, MQTT, `no_auth_user`, `auth_callout`, token or anonymous authentication, and JWT/operator/resolver authorization. Reject any deployment scope whose other access paths cannot be closed.

Add the upstream `github.com/nats-io/nats-server/v2/conf` parser dependency; do not handroll NATS configuration parsing. Use its includes, configuration-local variables and configuration-digest semantics. Run parsing in a short-lived helper invocation of the existing binary with a controlled environment that inherits no external configuration variables. Resolve included files only from the supplied deployment sources; explicitly refuse references requiring external environment variables in this initial supported profile. Never mutate the long-running server process environment, and never log credential values or credential-bearing URLs. Follow the repository's dependency and vendoring workflow and verify the affected production binaries still build with `CGO_ENABLED=0`; record the dependency and static-build impact rather than assuming the parser's small import surface makes it irrelevant. Pin supported semantics to the reported broker version, initially the repository's NATS 2.14 fixture version; unvalidated version combinations fail closed. Match the analyzed digest to the broker's loaded `config_digest` exposed by VARZ, including after reload. This proves the analyzed configuration matches the reported loaded source under the supported parser semantics; it does not prove credential custody or absence of command-line authentication overrides.

Use three distinct evidence sources:

- **Trusted operator authority:** the complete effective NATS configuration, including includes, resolved variables and permission defaults; every participating broker/account identity; its deployment revision; and an exhaustive credential-custody inventory covering Kubernetes, CLI, automation holders and credential issuers. Bind analyzed configuration to each broker's loaded digest and corroborate absence of command-line authentication overrides using actual broker pod arguments and configuration references. Reject unresolved variables, unaccounted broker nodes, unsupported launch mechanisms or missing override evidence. Completeness of credential custody remains an explicit operator trust boundary: neither CONNZ, USER.INFO nor a matching configuration digest proves it.
- **NATS system access:** actual broker/account identity, reported server version, loaded configuration digest and current connections. Reconcile these against the authorization inventory on every probe and renewal; use connection data to detect contradictions, never to establish completeness. Verify the system-authorized VARZ observation path against the pinned broker in integration tests.
- **Kubernetes API:** actual declared and running workloads, image digests, ServiceAccounts, pod arguments and credential references within the authority’s complete deployment scope. Include dormant ReplicaSets, scaled-to-zero controllers, Jobs/CronJobs and other admitted workload kinds. Read relevant RoleBinding and ClusterRoleBinding evidence as corroboration of credential custody where practical; do not infer exhaustive custody from RBAC alone. Reuse the repository's existing `kubectl` execution approach without introducing client-go or a general Kubernetes security controller. Unsupported workload, credential-distribution or inspection scopes fail closed.

Represent the operator source as a structured, authenticated deployment record using the existing Kubernetes configuration/Secret seams. Specify its permitted writers as trusted deployment operators. It must contain or reference actual configuration material and credential-holder mappings, not a boolean approval or handwritten `consumer_access_evidence` value. Do not add a controller, signing service or environment manager.

Treat completeness and active-configuration binding as explicit authority assertions, then verify their concrete contents against runtime observations. Authentication alone does not make an incomplete or incorrect inventory true. If a deployment cannot supply that trusted binding, it is unsupported and distributed activation remains blocked.

### 2. Verify enforceable exclusion

Evaluate effective NATS publish and subscribe permissions for **every configured principal**, including inherited defaults, wildcards and deny precedence. Explicitly enumerate the pinned broker's protected subjects: pull `MSG.NEXT`; ad-hoc, create, durable-create and delete consumer APIs; stream create/update/delete/purge, message get/delete and direct-get APIs; acknowledgment subjects, including applicable server-version prefixes; and lease/rollout KV subjects plus their backing-stream management APIs. Cover response and delivery subscriptions where they participate in access. Reject unrecognized protected API variants rather than assuming they are harmless.

Every principal able to consume the shared queue must have exclusively compatible, inventoried holders. Any incompatible or unknown holder must lose effective access through broker-enforced credential revocation, rotation or ACL exclusion. An old process retaining an unrestricted shared credential prevents activation, even when disconnected.

Apply the same analysis to principals able to create or alter the shared stream/consumer. Include old `EnsureSchema` callers. Either their holders are compatible and inventoried, or their credentials must be excluded. Preserve current queue topology; do not assume a consumer-only ACL addresses topology mutation.

Map compatibility to a trusted build identity, such as an operator-approved immutable image digest associated with the tested binary. Heartbeat capability declarations corroborate this mapping; they cannot establish it independently. Explicitly inventory non-Kubernetes credential holders and credential-distribution authorities. Unknown holders deny activation.

### 3. Wire the production verifier through existing seams

Implement the privileged authority adapter inside the existing server process and a separate stored-proof `PortDistributedActivationVerifier` for server, runner and CLI admission paths. Only the configured server workload hosting the authority refresher receives NATS system credentials and Kubernetes read-only permissions. Ordinary runners, CLI invocations and launch checks require neither. Raw Mongo and arbitrary stored evidence strings remain insufficient to certify a deployment.

Keep the privileged adapter narrowly divided into:

1. Loading and validating the trusted authorization/deployment record.
2. Parsing the supported static NATS authorization configuration and comparing its digest and supported semantics to the running brokers.
3. Reading NATS system observations.
4. Reading Kubernetes workload, launch-argument and credential-reference evidence.
5. Producing a canonical structured verified snapshot or refusal reasons.

Use the explicit optional configuration keys `contracts.distributed.system_nats_url`, `contracts.distributed.authority_ref`, `contracts.distributed.kubernetes_context` and `contracts.distributed.kubernetes_namespaces`. Supply credential-bearing URL overrides through explicit server-container `env` entries using `valueFrom.secretKeyRef`, taking precedence over shared ConfigMap `envFrom`; do not put the system URL in that shared ConfigMap or render it into logs. Use supported URL userinfo authentication rather than introducing a separate credential subsystem. Distributed admission remains default-off. Assign distinguishable connection names to compatible server/runner/CLI processes; names remain diagnostic evidence.

The existing chart gives server and runner the same ServiceAccount, and the runner sandbox Role can read namespace Secrets, create arbitrary pods and execute into pods. A ServiceAccount-name split alone therefore cannot confine authority credentials: a runner can otherwise copy the Secret or create a pod using the server identity. Refuse authority activation in such a shared namespace unless actual enforceable restrictions establish the required separation. Do not add an admission controller or general Kubernetes security auditor to obtain that separation.

Use two existing chart releases in distinct namespaces for the concrete positive fixture and operator recipe. The trusted server release sets `runner.enabled=false`, uses its own existing `serviceAccount.name` seam, and renders no runner sandbox Role/RoleBinding. The worker release sets `server.replicas=0`, disables the dormant server's HPA, uses a separate ServiceAccount, and receives no system or authority Secrets. Sandboxes continue using the existing runner namespace behavior. Both releases retain the same NATS broker/account/stream/consumer and the same Store. Add only the opt-in template guards or server-only Secret wiring needed for this profile; with distributed authority disabled, existing default deployments and RBAC remain unchanged.

Treat every authority-hosting server and refresher credential holder, together with credential issuers, as part of the trusted inventory. Verify the specific namespace boundary using declared custody and relevant actual RBAC evidence: worker identities must not read trusted namespace Secrets, pods or RBAC, create pods or execute into pods there, or have equivalent impersonation or RBAC-mutation paths that bypass those denials. Missing evidence, unexplained cross-namespace grants or unsupported privilege paths refuse activation. Namespace names and ServiceAccount names alone are not proof.

Host a 20-second authority refresher in the existing server lifecycle. Select and fence its writer using the existing lease abstraction and Mongo compare-and-swap, without a new service. Each renewal performs the privileged observations and may update only an already Enabled activation record with the same authority fingerprint, epoch and policy revision. It must never enable a record, replace an explicit Disable, or authorize a changed fingerprint. Keep operator `policy_revision` separate from freshness `proof_revision`; renewal does not advance the operator revision. Refresh CAS predicates include Enabled, the observed policy revision, proof revision and current lease ownership/fencing token. Disable atomically clears Enabled and advances the policy revision without depending on the frequently changing proof revision, so normal refresh traffic cannot starve Disable. Any refresh issued against the preceding policy revision then fails.

Implement 20-second instance capability heartbeats through the existing NATS KV/lease plumbing in the configured runner-rollout bucket, whose default is `iterion-runner-rollout`, under the separate key prefix `ports-v1.census.<principal>.<instance>`. Records identify principal, instance, build, access scope and epoch. Enforce their logical 60-second freshness in the verifier without changing the shared bucket TTL or existing monotonic rollout keys. Protect the corresponding KV subjects and backing-stream APIs in the permission evaluation; principal identity and write scope must match the closed authorization inventory. Verify with the pinned-main binary that old `EnsureSchema` leaves these keys intact. The current per-run `iterion.heartbeat` is not a fleet census; fleet heartbeats corroborate the closed operator inventory and do not create authority.

Keep `contracts inspect` read-only and explanatory. Route distributed `contracts probe` through an authenticated operator-only handler in the existing server to run the privileged adapter and persist a candidate verified snapshot without enabling admission or modifying Disable. Route `contracts activate` through the same trusted server boundary to atomically enable only a fresh, matching candidate and expected policy revision. Ordinary direct-filesystem command behavior remains as approved. Neither command provisions cloud permissions or edits Kubernetes/NATS configuration.

Restrict verified-snapshot, refresh and activation writes to these trusted server paths. Do not expose an endpoint that accepts caller-supplied verification status or arbitrary proof contents; tenant launch callers cannot authorize themselves. Database administrators remain within the stated administrative trust boundary. Launch-time verifiers read only the stored structured snapshot and policy, validating provenance through that restricted write contract, schema, backend identity, epoch, fingerprint, authority/policy revision, age, local binary capability and queue identity before admitting each new root.

### 4. Preserve freshness, epochs and accepted runs

Retain 20-second heartbeat and 60-second proof-freshness defaults. Fingerprint backend/database identity, queue topology, effective authorization, credential custody, workload/build identities and authority revision.

Missing observations, failed reads, unsupported authorization, stale evidence or changed fingerprints deny new native roots. The refresher records invalidation with a fenced CAS when it can reach the Store; if an outage prevents that write, the previous proof expires no later than 60 seconds after its last successful verification. Launch checks never extend freshness. A changed fingerprint requires an explicit new probe/epoch/activation sequence and cannot be accepted by automatic renewal. Activation must reject a proof superseded during probing or activation. Refresh and activation CAS operations must lose to a concurrent Disable or policy-revision change.

Document the authority’s change protocol: disable native admission before changing authorization, credential custody or admitted workload capabilities; advance the monotonic epoch; apply the change; re-probe; reactivate. Periodic observation is not an instantaneous change detector and cannot replace this protocol. Trusted operators and credential issuers form the explicit administrative trust boundary.

Continue already admitted native runs and their required descendants/recovery work across disablement or proof expiry. Their persisted admission identity remains authoritative. Retain capable consumers and native namespace protection during rollback.

### 5. Prove the adapter with disposable integration fixtures

Extend the existing `tests.yml` NATS conformance and kind+Helm cloud-e2e fixture paths with opt-in disposable coverage using the pinned NATS version, real static authorization and system access, the existing Mongo fixture, and a disposable Kubernetes API/cluster. Use the two existing chart releases in distinct namespaces described above, pointing both releases at the same broker/account/queue and Store. Supply fixture credentials through explicit Secret-backed URL userinfo overrides. Add Helm assertions for unchanged disabled defaults, server-only system Secret references, distinct release identities, no sandbox Role/RoleBinding in the trusted release, and zero worker-release server replicas with its HPA disabled. Regular filesystem use and the default test path must not require Docker, NATS, Mongo or Kubernetes.

Run the **production authority adapter** in the positive integration case; do not substitute the fixture verifier currently injected into Store tests. Exercise:

- Positive activation with finite credentials, compatible immutable builds, complete custody, matched runtime observations and fresh evidence. In kind, exercise actual worker-identity denials for reading trusted namespace Secrets, pods and RBAC, creating pods there, and executing into the trusted server. Prove the real adapter refuses the shared-namespace broad sandbox Role and refuses an introduced cross-namespace privilege grant. Include authority/refresher holders and credential issuers in the positive inventory; do not treat the namespace split alone as sufficient.
- Actual pinned-main binaries from SHA `3872f9dd1d1cbf9c18ed338c66c9f55aaaea3fcc` denied queue access by ACL or revoked credentials, including an attempted old `EnsureSchema` connection.
- Legacy v14 and native v15 delivery through the same stream/consumer after exclusion, including delayed native work without old-consumer MaxDeliver exhaustion.
- Refusal for authless/shared unrestricted access with unknown holders, a disconnected authorized old holder, an old scaled-to-zero workload, unknown connections, mismatched account/configuration binding, unsupported authorization, inaccessible Kubernetes scope and incomplete custody.
- Differential integration tests comparing the permission evaluator's decisions with real broker allow/deny behavior for every fixture principal across the enumerated protected APIs, ACK variants and lease/rollout KV resources. Include wildcard grants, defaults, deny precedence, response/delivery subscriptions, configuration includes/variables, unsupported authorization paths, parser/server version mismatch, command-line override refusal and digest change after reload.
- Repeated successful 20-second renewals beyond the initial 60-second proof lifetime; authority/Kubernetes/NATS outages and expiry within 60 seconds; refresh-versus-Disable and competing-refresher fencing races; fingerprint changes requiring explicit reactivation; rejected tenant proof injection; and new-root admission by ordinary components without privileged credentials. Verify Disable succeeds during repeated freshness revisions and no stale refresh restores admission. Exercise census-key freshness, protected write scope and preservation under pinned-main `EnsureSchema`. Also cover epoch races, rollback and continued completion of already admitted native runs.

Use unit fixtures for parser and Kubernetes object-shape coverage; distinguish those results from integration results. **All proposed tests are currently `not_run`.**

### 6. Operator path, limitations and decision boundary

Document how an operator obtains the authority record from actual NATS configuration sources and exhaustive credential custody, selects the existing Kubernetes scope, supplies system access only to the server refresher through existing Secret seams, and runs inspect/probe/activate through the trusted server operator path. Provide the two-release, distinct-namespace recipe using the existing chart seams, including the disabled worker-release server HPA and absence of the trusted-release sandbox Role. Explain why a ServiceAccount split within the existing broad sandbox namespace is insufficient, and identify the specific privilege-boundary evidence required before activation. Explain the configuration-digest comparison, actual pod-argument checks, controlled parser environment, unsupported-profile refusals and remaining operator responsibility for custody completeness. The unauthenticated cloud-compose configuration is outside the supported static-authentication profile and must refuse distributed native activation. Chart defaults alone supply no evidence of a qualifying deployment. This recipe authorizes disposable fixture provisioning and code/documentation work only; production mutation and rollout recommendations remain unavailable until actual deployment evidence establishes the proof.

No production deployment, credential rotation, configuration changes, paid runs or merge are authorized by this addendum. No live deployment verification has occurred; current Kubernetes permissions and absent NATS system credentials prevent such a claim.

The code and disposable proof can proceed within the approved architecture. Production activation remains conditional on a complete trusted authority source and enforceable exclusion of incompatible credentials. If the actual deployment cannot meet those conditions, record that precise blocker. Adopting a separate native stream would require a concrete architecture decision reopening the approved same-queue constraint; it is not a fallback authorized here.
