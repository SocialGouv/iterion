# Writing to the iterion board

> **Nexie boundary.** The `whats-next` conversational node is deliberately
> granted only `board.read`. Use `list_issues`, `get_issue` and `list_labels`
> directly, but express every write through the `assistant_actions` contract
> in its system prompt. The Studio validates those arguments and enforces the
> operator's per-action policy. The mutating MCP tools below document ordinary
> workflow nodes that hold the corresponding capability; they are not an
> escape hatch for Nexie.

Iterion runtime registers an internal MCP server (`__mcp-board`) for any
agent/judge node whose `capabilities:` list contains a `board.*` entry.
The server exposes these tools, each gated by a single capability:

| Tool FQN | Capability | Purpose |
|---|---|---|
| `mcp__iterion_board__create_issue` | `board.create` | Create a new issue. |
| `mcp__iterion_board__transition_issue` | `board.move` | Move an issue between states. |
| `mcp__iterion_board__set_bot` | `board.assign` | Choose which bot runs the issue — the canonical dispatcher selector. |
| `mcp__iterion_board__assign_issue` | `board.assign` | Set the human/team owner. NOT for bot selection (use set_bot). |
| `mcp__iterion_board__set_labels` | `board.label` | Replace the issue's label list. |
| `mcp__iterion_board__close_issue` | `board.close` | Move the issue to a terminal state. |
| `mcp__iterion_board__comment_issue` | `board.comment` | Append a markdown comment to an issue. |
| `mcp__iterion_board__list_issues` | `board.read` | List issues (optionally filtered). |
| `mcp__iterion_board__get_issue` | `board.read` | Fetch one issue by ID or short prefix. |
| `mcp__iterion_board__list_labels` | `board.read` | List distinct labels in use, with counts. |

A node only sees the tools its capabilities unlock — anything else is
absent from `tools/list` and rejected with a `capability denied` error
if called directly.

## Tool input shapes

### `create_issue` (board.create)

```json
{
  "title": "Refactor X (required)",
  "body": "Markdown body — the framed template below.",
  "state": "backlog",
  "labels": ["horizon:next", "source:whats-next"],
  "priority": 5,
  "blockers": ["native:abcd1234"],
  "bot": "feature-dev",
  "bot_args": {"feature_prompt": "Add CSV export to the reports page"},
  "fields": {"note": "optional freeform metadata"}
}
```

`bot` is the CANONICAL routing selector (the dispatcher routes by bot
first, falling back to `assignee` only when bot is empty), and
`bot_args` carries per-ticket workflow-var overrides applied at launch
(`--var key=value`). `assignee` is the human/team owner — not the bot.
`fields` is freeform metadata, validated against the board schema.

Returns the created `Issue` object. `id` is autogenerated as
`native:<uuid>` — capture it for downstream calls.

**Framed-ticket bodies.** Every ticket created for dispatch uses the
3-section body — `## Context` / `## Done criteria` / `## Verify` — the
anti-façade contract the closer reads before declaring it delivered.
Template and rules in `roadmap-synthesis`.

### `transition_issue` (board.move)

```json
{"id": "native:abcd...", "to": "ready"}
```

`id` accepts unambiguous prefixes (first 8 chars of the UUID work).
Fails with `unknown state` if `to` is not declared on the board.

### `set_bot` (board.assign)

```json
{"id": "native:abcd...", "bot": "feature_dev"}
```

Sets the issue's **bot** — the canonical way to choose which workflow
the dispatcher runs. The dispatcher routes by `bot` first, falling back
to `assignee` only when `bot` is empty (the path external trackers like
GitHub/Forgejo rely on, since they have no bot field). A bot name that
resolves to a file but isn't in the dispatcher's `assignee_workflows`
is **skipped with a warning** rather than silently running the default
workflow, so a typo'd bot fails loudly. Names are matched tolerantly
(`feature_dev` ≡ `feature-dev` ≡ `Feature Dev`). Empty string clears it.

**Prefer set_bot over assign_issue for "run bot X".** Use assign_issue
only to record a human/team owner.

### `assign_issue` (board.assign)

```json
{"id": "native:abcd...", "assignee": "alice"}
```

Sets the human/team **owner**. Empty string clears it. This is NOT the
bot selector for the native tracker — use `set_bot`. (On GitHub/Forgejo,
where there is no bot field, the assignee doubles as the routing key via
`assignee_workflows`.)

### `set_labels` (board.label)

```json
{"id": "native:abcd...", "labels": ["chore", "blocked"]}
```

Replaces — does not merge. Pass an empty array to clear.

### `close_issue` (board.close)

```json
{"id": "native:abcd...", "to": "done"}
```

`to` is optional; when omitted, defaults to the board's first terminal
state. Rejects non-terminal targets.

### `comment_issue` (board.comment)

```json
{"id": "native:abcd...", "body": "closing as superseded by native:ef01 — delivered in 9dc026b0"}
```

Appends a markdown comment that outlives the chat. Use it to trace a
decision before `close_issue` (one-line rationale with the evidence),
to record a delivery verification ("`## Verify` bullets checked against
`pkg/foo/bar.go` at f8dd03e"), or to explain a re-triage.

### `list_issues` (board.read) + `get_issue` (board.read) + `list_labels` (board.read)

```json
{"state": "ready", "label": "horizon:next", "assignee": "feature_dev"}
```

All filter fields are optional. `get_issue` takes `{"id": "..."}`.
`list_labels` takes `{}` and returns the distinct labels in use with
their counts — call it FIRST before labelling anything, and reuse the
operator's vocabulary (see `iterion-label-vocabulary`).

## Kanban states

The default board ships these states:

| Name | Terminal | Eligible | Notes |
|---|---|---|---|
| `inbox` | no | no | Bot-emitted findings land here. Operator triages → backlog (promote) or deletes (dismiss). |
| `backlog` | no | no | Initial state — drafts not yet ready. |
| `ready` | no | **yes** | The dispatcher polls this and dispatches. |
| `in_progress` | no | yes | Dispatcher flips an issue here on claim. |
| `review` | no | no | Bot done, waiting on human review. |
| `done` | **yes** | no | Successful terminal state. |
| `blocked` | **yes** | no | Failure terminal state. |

When a bot has board.create capability and wants to surface an
out-of-scope observation (instead of acting on it), `create_issue`
with `state: "inbox"` plus a `findings` label is the canonical
shape. The operator decides whether to promote the issue to
backlog or dismiss it.

A workflow can customise the board (different names/colors) via
`iterion issue board init`; the labels above are conventions, not
DSL-enforced names.

## The "move to eligible → dispatcher dispatch" pattern

Whenever you create an issue you want the dispatcher to pick up
immediately, set `state: "ready"` in the create_issue call (or call
`transition_issue` right after). The dispatcher's polling loop walks
the board and dispatches issues whose state has `eligible: true`. If
you leave the issue in `backlog`, it stays as a draft until a human
or another bot moves it forward.

```
create_issue(..., state="ready") ──┐
                                    ├─→ dispatcher poll → dispatch to bot
transition_issue(id, "ready")    ──┘
```

**Limited-ready-lot discipline.** Move **≤ ~5 issues to `ready` per
turn**, even when a study batch is larger. The dispatcher typically
serialises (`max_concurrent: 1`) so a big ready lot just queues, burns
the daily cost cap faster, and stresses provider rate limits. Leave the
rest in `backlog` — they surface next turn as the lot drains. Rationale
and the other factory rules: `factory-ops`.

## Common error cases

- **`capability denied`** (`-32601`): the node was not granted the
  required `board.*` capability. Add it to the `capabilities:` list on
  the agent/judge declaration.
- **`unknown state`**: target state isn't declared on the board. Use
  `list_issues` to discover the board, or run
  `iterion issue board show` from a shell.
- **`board has no terminal state`**: only fires on `close_issue` when
  no terminal state is configured. Pass `to:` explicitly or fix the
  board.
- **`required field <name> missing`**: the board declares a required
  custom field that wasn't provided. Add the field to
  `create_issue.fields` or unset the requirement.

## Sandbox runs (containerised bots)

When the workflow runs with `sandbox:` active, the host's iterion
binary isn't reachable inside the container. The runtime falls back
to an HTTP transport (`/api/v1/mcp/board` on the iterion server),
authenticated via an ephemeral `X-Iterion-Run` token. Both paths
expose the same tool set and the same error semantics.

## Quick sanity check

After your workflow run finishes, you can inspect the resulting
board from a shell:

```bash
iterion issue list --store-dir <workspace>/.iterion/dispatcher
iterion issue board show --store-dir <workspace>/.iterion/dispatcher
```

Or via the studio at `/board` if `iterion studio` is running on the
same workspace.
